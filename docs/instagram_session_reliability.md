# Instagram 수집 리디렉션 진단과 개선 설계

진단일: 2026-09-26 (KST). 이 문서는 조사 결과와 구현 계획이며, 수집 복구 완료 보고가 아니다.

## 실제 관찰

| 비교 | 결과 |
| --- | --- |
| 현재 수집기, 저장된 세션, 레퍼런스 프로필 GET | HTTP 302 → Instagram 홈 → 홈으로 302 반복 |
| 동일 URL·헤더, 로그인 쿠키 없는 별도 requests.Session, 1회 GET | HTTP 200, 응답에 대상 계정명 포함 |
| 현재 Chrome의 동일 수집용 계정, 같은 레퍼런스 프로필 방문 | 프로필·게시물 목록 정상 표시 |
| 동일 Chrome의 해당 계정 릴스 탭 | 게시물 링크와 조회수 표시 확인 |
| 수집용 세션 파일 최종 수정 | 2026-09-23 01:05:54 KST |
| 9월 25일 / 26일 예약 수집 | 오전 7시 시작, 각각 12계정 실패, 신규 수집 0건 |

HTTP 진단은 리디렉션 자동 추적을 끄고 최대 4회로 제한했다. 쿠키 값, 토큰,
응답 본문은 기록하지 않았다. 익명 HTTP 200은 전체 수집이나 조회수 확보 성공을 뜻하지 않는다.
브라우저 화면의 부가 배수 표시 등 확장 프로그램이 넣었을 수 있는 값은 판정 근거로 사용하지 않았다.

## 결론과 확신 수준

- **확인됨:** 현재 수집기의 저장 쿠키를 사용하는 요청 경로에서 실패한다. 일반 Chrome의
  로그인 상태와 수집기의 세션 파일은 별개다. 사용자가 브라우저에서 인증했다고 파일이 자동 갱신되지 않는다.
- **확인됨:** 이번 오류는 최초 프로필 HTML 단계에서 발생한다. 이후 GraphQL 쿼리 ID 변경은
  이번 리디렉션의 직접 원인이 될 수 없다.
- **강한 근거:** 전체 계정 정지나 일반적인 접속 장애보다, 저장 쿠키의 상태 또는 해당 쿠키와
  HTTP 클라이언트 조합의 문제가 우선이다. 브라우저와 requests는 쿠키·실행 환경이 모두 달라
  둘 중 하나만을 단독 원인으로 확정할 수는 없다.
- **미확정:** 특정 쿠키 폐기/변경, 서버 측 세션 제한, 브라우저와 다른 클라이언트 실행 방식 중
  어느 것이 302를 유발했는지는 아직 분리 검증하지 않았다. Instagram은 이 응답에 원인을 명시하지 않았다.
- **배제 불가:** 쿠키 없이 200이라는 결과만으로 로그인 요청에 대한 제한까지 없다고 결론내릴 수 없다.

## 코드에서 확인한 구조적 문제

1. `instagram_login.py`는 별도 영속 Chrome에서 쿠키를 꺼내 Instaloader 파일로 저장한다.
   정기 수집 `web_graphql.py`는 이 파일을 requests로 읽으며 브라우저 프로필을 사용하지 않는다.
   즉, 로그인과 일일 수집이 동일한 환경을 공유하지 않는다.
2. 설치된 Instaloader의 `save_session`은 cookie jar를 이름/값 딕셔너리로 변환하고,
   `load_session`은 이 딕셔너리에서 jar를 복원한다. 도메인·경로·만료 등 원래 메타데이터가
   보존되지 않는다. 실제 로드된 쿠키들의 도메인은 비어 있었다. 이것만으로 장애 원인이 증명되지는 않는다.
3. `WebGraphQLCollector`는 시작 시 파일을 읽지만 수집 중 변경된 쿠키를 파일에 저장하지 않는다.
   세션 갱신이 있어도 다음 날 같은 오래된 상태로 시작할 수 있다.
4. 로그인 성공 검사는 Instaloader의 별도 GraphQL `test_login()`이다.
   정기 수집의 프로필 → 게시물 → 조회수 경로를 검사하지 않으므로 로그인 검사와 수집 가능 여부가 다를 수 있다.
5. 로그인 검증은 Mac Chrome 128, 웹 수집기는 Mac Chrome 150 헤더를 고정 사용한다.
   Windows의 실제 브라우저와 다르다. 환경 불일치는 확인됐지만 이번 오류의 단독 원인으로 확정하지 않았다.
6. 최초 GET은 최대 30회 리디렉션을 따라간다. 공통 로그인 장애가 나도 12개 계정에서 반복한다.
   로그인 장애·프로필 삭제·요청 제한·서버 오류를 구분한 중단 정책이 없다.
7. 실패 알림은 로컬 DB에 남지만 홈 대시보드는 과거 리포트를 유지한다.
   작업 실행 여부, 데이터 최신성, 실제 수집 성공을 사용자가 한눈에 구분하기 어렵다.

## 우선순위

### P0 — 공통 장애 감지와 정확한 상태 표시

- 수집 시작 전에 실제 수집 경로로 1개 계정의 프로필·게시물 접근을 검사한다.
- HTTP 상태, 리디렉션 경로 유형, 인증 필요 여부를 비밀값 없이 기록한다.
- 자기 자신으로의 리디렉션은 짧게 중단한다. 일반 프로필 오류는 해당 계정만 실패 처리한다.
- 확인된 인증/계정 확인 장애는 전체 순회를 중단한다. 모호한 루프는 제한된 교차 확인으로
  공통 장애인지 판단하고 중단한다. 미시도 계정을 실패로 부풀리지 않는다.
- 실행 시각 / 마지막 성공 수집 시각 / 성공·실패·건너뜀 / 조회수 확보율을 분리한다.
- 인증 요구는 사용자에게 알린 뒤 대기한다. 제한·일시 장애는 정해진 간격과 횟수 내에서만 재시도한다.

### P1 — 로그인과 수집 환경 통합

권장안은 **전용 영속 Chrome 프로필에서 로그인과 정상 페이지 기반 수집을 함께 수행**하는 것이다.

- 현재 로그인 전용 프로필을 수집에도 사용하도록 collector를 추가한다.
- 일반 Chrome 사용자 프로필을 강제로 다른 프로세스에서 열거나 쿠키 파일을 반복 복사하지 않는다.
- 브라우저가 정상적으로 로드한 페이지에서 계정·게시물·날짜·조회수·캡션을 추출한다.
- 고정 게시물은 게시일 기준으로 처리하고, 마지막 수집 경계까지 필요한 만큼만 순회한다.
- `1.2만` 등 축약된 조회수는 원문과 근삿값 여부를 보관한다. 정확한 수치와 섞어
  작은 증가율을 확정하지 않으며, 누락은 0이 아닌 미확인으로 처리한다.
- 인증을 마친 후 실제 수집 경로가 통과해야 준비 완료로 표시한다.
- 브라우저가 만료·계정 확인 화면을 보이면 정상 사용자 인증을 요청한다.
- 프로필 사용 잠금, Windows 로그인 상태, 브라우저 비정상 종료 복구를 예약 실행 계약에 포함한다.

이 방식은 쿠키 이식과 클라이언트 불일치를 줄이는 개선안이지, 영구 로그인 보장이나
플랫폼 제한 해제 수단이 아니다. UI 변경 대응과 브라우저 실행 비용도 필요하다.

현재 정상 사용 중인 Chrome에 로컬 수집 확장을 붙이는 대안도 있다. 재인증 부담을 줄일 수 있지만
확장 설치·권한, Chrome 상시 실행, 사용자 탭과의 충돌을 별도로 설계해야 한다.
두 방식 중 기존 코드와 연결하기 쉬운 전용 프로필부터 검증한다.

### P2 — 공식 API의 적용 범위 확인

공식 API로 가져올 수 있는 계정·필드는 그 경로를 우선 검토한다. 다만 레퍼런스 전체의
계정 유형, 권한, 다른 계정 릴스 조회수 제공 여부를 실제로 검증하기 전에는 전면 대체를 약속하지 않는다.
이번 조사에서 Meta 문서 원문 일부는 접근 제한으로 확인하지 못했다.

## 검증 순서와 완료 기준

1. 전용 프로필에서 동일 계정·동일 레퍼런스 1개로 로그인 → 프로필 → 릴스 → 수치 저장을 검증한다.
2. 브라우저를 정상 종료한 뒤 재실행해 재로그인 없이 같은 경로가 되는지 확인한다.
3. 12개 계정을 순차 수집하고 필드별 완전성, 중복, 고정 게시물, 날짜 경계를 검사한다.
4. 스케줄러로 실행한 경우에도 같은 프로필과 저장 경로를 사용하는지 확인한다.
5. 3일 연속 오전 7시 실운영을 관찰한다. 단일 성공을 안정화 완료로 간주하지 않는다.
6. 인증 필요·429·네트워크 끊김을 모의 시험해 중단/재시도/오래된 데이터 표시가 정확한지 확인한다.

## 구현 현황 (2026-09-26)

- 기본 수집기를 `browser`로 전환했다. 명시적 `--source web`은 레거시 진단용으로 유지한다.
- 로그인과 수집은 `data/instagram_browser` 하나를 사용한다. 프로필 잠금은 별도 프로세스의
  로그인과 수집이 충돌하지 않도록 한다. 기존 브라우저 프로필과 세션 파일을 삭제하지 않는다.
- 정상 페이지가 받은 게시물 JSON과 페이지의 게시물 링크를 대조한다. 별도 GraphQL 요청을 만들지 않는다.
- 인증 사전 점검과 실행 중 공통 장애 감지, 미시도 계정 집계, 종료 시 브라우저 정리를 연결했다.
- Windows 예약 실행은 네트워크 시간 초과/서버 장애/프로필 사용 중에 한해 300초 뒤 한 번 재시도한다.
  로그인 필요/계정 확인/429에는 같은 실행에서 재시도하지 않는다.
- 홈 대시보드에 실행 결과, 데이터 갱신, 전체 성공, 정확한 조회수 확보 건수를 표시한다.
- 최초 사전 점검은 `login_required`였으나, 9월 26일 사용자가 전용 프로필 인증을 완료했다.
  로그인 프로세스 종료 후 Windows 예약 작업이 별도 프로세스에서 재로그인 없이 접속했다.
- 14:27~14:49 첫 복구 실행에서 11계정 성공, 1계정 실패, 게시물 376개 저장·갱신을 확인했다.
  실패 계정은 Instagram 자체에서 페이지를 사용할 수 없다고 표시했다. 계정명 변경·삭제·접근 제한 중
  어느 원인인지는 확정하지 않았고, 등록 계정 및 과거 데이터는 보존했다.
- 실운영 응답에서 JSON 본문이 `text/javascript`로 전달되고, 릴스 노드에는 게시일 없이 조회수만
  있는 경우를 확인했다. 응답 형식을 허용하고 동일 shortcode의 프로필·릴스 노드를 합치도록 수정했다.
  릴스 보강 스크롤은 선택된 프로필 게시물 범위를 유지한다. 수정 후 동일 계정 12/12 정확한 조회수 검증.
- 14:52~14:56 수정 후 Windows 예약 작업 재검증: 11계정 성공, 같은 접근 불가 계정 1개 실패,
  143개 게시물 갱신, 영상 지표 134건 중 정확한 조회수 123건(91.8%). 미확인 11건은 성공으로 처리하지 않았다.
  대시보드 API `partial_failure`, 작업 종료 코드 1, 다음 실행 9월 27일 07:00 KST를 확인했다.
  browser/login/operations 회귀 테스트 34개 통과. 실패 계정을 삭제하거나 결과를 전체 성공으로 바꾸지 않았다.
- 3일 연속 오전 7시 실행은 아직 검증하지 않았다. 단일 날짜의 성공을 장기 안정성으로 단정하지 않는다.

### 운영 명령 (프로젝트 디렉터리에서 실행)

```powershell
.\.venv\Scripts\python.exe -X utf8 -m hotpost login --browser dedicated
.\.venv\Scripts\python.exe -X utf8 -m hotpost run --source browser
.\.venv\Scripts\python.exe -X utf8 -m hotpost schedule status
```

로그인 명령은 전용 프로필의 계정과 레퍼런스 게시물 접근을 확인하고 창을 정상 종료한다.
`instagram_browser_ready.json`은 검증 시각과 개수만 가진 진단 파일이며, 인증 토큰이 아니다.
로그인 준비 확인 후에도 매 수집 시작 시 실제 로그인 상태를 다시 확인한다.
공식 API 연동은 권한과 제공 필드 확인이 필요한 별도 단계로 남겨두었다.
